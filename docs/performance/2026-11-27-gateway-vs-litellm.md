# 성능 비교: llm-gateway 대 litellm (2026-11-27)

> 상태: 단일 인스턴스 비교 완료. **시험 중 우리 게이트웨이의 결함(업스트림 유휴 연결)을 찾아 고쳤고, 우리 쪽 수치는 고친 뒤 다시 잰 값이다.** litellm 은 다시 재지 않았다. 스케일아웃(여러 대) 시험은 이 문서에 포함하지 않았다.
> 이 문서의 수치는 **로컬 Docker VM 기준의 상대 비교**다. 운영 서버(dell)의 성능이 아니다.

## 한눈에 보기

이 조건에서:

- 낮은 부하에서 우리 게이트웨이가 더하는 지연은 **약 2~3ms** 로, litellm(6~15ms)보다 작고 p99 도 더 낮다
- 한계 처리량은 같은 CPU 4코어에서 litellm 4워커의 **최소 1.3배**(초당 1000건 요청에도 포화하지 않았다), 동시 접속 200 에서는 **6.7배**(3788/s 대 567/s)
- 스트리밍 첫 토큰 지연은 부하가 낮으면 우리와 litellm 4워커가 비슷하고, litellm 1워커는 한계를 넘으면 크게 밀린다
- 메모리는 우리가 **수십 배 작다**(24~64MiB 대 0.7~3GiB)
- 업스트림 응답이 실제 모델처럼 1초 정도면 낮은 부하에서는 세 대상이 거의 같고, 차이는 한계 부하에서 드러난다
- 시험으로 **우리 게이트웨이의 실제 결함 하나를 찾아 고쳤다**(아래 "시험으로 찾은 결함")

각 시나리오를 **한 번씩만** 재서 반복 편차를 모른다. 수 배 차이는 믿을 만하지만 2.7ms 대 6.7ms 같은 작은 차이는 반복 측정이 필요하다.

## 시험 방법

### 업스트림은 가짜 LLM
진짜 모델은 응답이 느리고 매번 달라서 게이트웨이 자체의 오버헤드가 묻힌다. 두 게이트웨이가 같은 가짜 서버를 본다. 모델은 돌지 않고 정해 둔 응답을 정해 둔 시간 뒤에 돌려준다(토큰 사용량은 항상 10+20). 응답 `id` 는 요청마다 다르다.

| 조건 | 비스트림 | 스트림 |
|---|---|---|
| `fast` | 50ms | 첫 청크 50ms, 이어서 5ms 간격 20청크(총 약 160ms) |
| `real1s` | 1초 | 첫 청크 300ms, 이어서 40ms 간격 20청크(총 약 1.1초) |

`fast` 는 게이트웨이 오버헤드를 가려내려는 값이고, `real1s` 는 실제 모델에 가까운 값이다.

### 시나리오
- **일정한 도착 속도**(`rate-N`): 초당 N건을 30초. 느려져도 요청을 줄이지 않아 지연 백분위가 정확하다. 서버가 못 따라가면 "밀린 요청"으로 기록된다
- **일정한 동시 접속**(`vus-N`): N개 접속이 20초. 한 요청이 끝나야 다음을 보내므로 최대 처리량을 본다
- **스트림**(`stream-rate-100`): 초당 100건 스트리밍 30초. 첫 바이트까지 시간이 첫 토큰 지연의 근사치다
- 각 대상마다 시작 전 워밍업(10초, 결과 버림). 모두 가상 키로 인증한다
- `fast`: 초당 100·300·1000, 동시 접속 1·10·50·200, 스트림. `real1s`: 초당 100·300, 동시 접속 10·50·200, 스트림

### 공정성 장치
- 세 대상이 같은 자원 제한, 같은 업스트림, 같은 PostgreSQL 메모리 디스크
- litellm 은 두 가지: **1워커**(dell 과 같은 실행 방식 `--config ... --port 4000`)와 **4워커**(`--num_workers 4`)
- 두 쪽의 모델에 같은 단가를 줘서 비용 집계 경로를 같이 타게 했다
- 한 번에 하나만 띄운다
- **정합성 확인**: 시험 뒤 k6 가 보낸 요청 수와 DB 의 사용량 기록 수를 비교한다(한쪽만 기록을 안 하면 비교가 무의미하다). 세 대상 모두 맞았다(차이는 워밍업 분량뿐)

## 시험으로 찾은 결함 (수정 완료)

첫 측정에서 우리 게이트웨이의 `fast` 동시 접속 200 구간이 이상했다. 처리량이 동시 접속 50(929.8/s)보다 낮은 744.0/s, p99 3.2초, 실패 1.03%, CPU 436% 였다. 응답 코드별 집계와 서버 로그를 더해 다시 재서 원인을 확인했다.

| | 내용 |
|---|---|
| 증상 | 높은 부하에서 503 `Upstream unavailable ... The model server did not respond`. 동시 접속 200 직후의 초당 300건 시험은 연결 단계에서 바로 53% 실패(앞 시험이 남긴 닫힌 연결 때문) |
| 원인 | 서버 로그 300건이 전부 `dial tcp ...: connect: cannot assign requested address`, 즉 **임시 포트 고갈**. 업스트림으로 가는 HTTP 클라이언트가 Go 기본값을 복제해서 쓰는데, 이 기본값은 같은 호스트에 대해 **유휴 연결을 2개까지만** 보관한다. 동시 요청이 2개를 넘으면 응답마다 연결을 닫고 새로 맺고, 닫힌 연결이 `TIME_WAIT` 로 쌓여 포트가 바닥난다 |
| 영향 | 모델 서버가 한 곳이면 운영에서도 초당 수백 건부터 같은 일이 생긴다. 연결을 계속 새로 맺느라 CPU 도 썼다 |
| 수정 | `internal/app/app.go` 의 업스트림 클라이언트가 유휴 연결을 호스트당 1024개, 전체 2048개까지 보관한다 |
| 시험 | `TestUpstreamClient_ReusesConnectionsUnderConcurrency`: 동시 요청 100개를 두 번 보내 두 번째에 새 연결이 몇 개 생기는지 센다. **고치기 전 98개(실패), 고친 뒤 통과** |

고치기 전후 비교(`fast`, 우리):

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 동시 접속 200 처리량 | 744.0/s | **3787.8/s** |
| 동시 접속 200 p50 / p99 | 178.5 / 3208.7ms | **52.1 / 58.6ms** |
| 동시 접속 200 실패 | 1.03% | **0%** |
| 동시 접속 200 CPU 최대 | 436% | **79%** |
| 그 밖의 시나리오 | 측정 편차 안에서 같다(동시 접속 50 만 929.8 → 850.1/s, 앞선 재측정에서도 865~894/s 를 오갔다) | |

고친 뒤 전체 시나리오(`fast`·`real1s`)의 응답 161,802건이 **모두 200** 이었다.

litellm 1워커의 실패(1.6%, 503)는 **다른 원인**이다. 응답 본문이 `Service Unavailable, the authentication database is temporarily unreachable` 로, 과부하에서 litellm 자체의 DB 연결이 막힌 것이다. 이번에 고친 것과 무관하다.

수정 전의 우리 측정값은 `bench/results/<RUN_ID>/gateway-before-fix/` 에 보관했다(git 에서 제외되므로 위 표가 기록이다).

## 해석과 한계
1. **각 시나리오를 한 번씩만 쟀다.** 반복 편차를 모른다. 작은 차이는 결론으로 쓰지 않는다.
2. **litellm 의 값은 시험 묶음마다 크게 다를 수 있다.** 동시 접속 50 의 litellm 1워커가 본시험에서 147.8/s, 재측정(같은 컴퓨터, 다른 순서)에서 222.9/s 로 약 50% 차이가 났다. 원인은 확인하지 못했다. litellm 의 절대 수치와 우리와의 배수는 이 편차 안에서 읽는다. 방향(우리가 앞선다)은 바뀌지 않았다.
3. **같은 단위의 비교가 아니다.** 우리는 Go 프로세스 하나가 4코어를 모두 쓰고, litellm 1워커는 파이썬 프로세스 하나다. 4워커 비교가 더 공정하다.
4. **litellm 4워커가 메모리 제한(3GiB)에 닿았다.** 4워커의 한계가 CPU 가 아니라 메모리 제한 때문일 수 있다. 제한을 늘려 다시 재야 진짜 한계를 말할 수 있다.
5. 부하 생성기가 같은 VM 에서 돈다. 절대값은 노트북 기준이고 운영 성능이 아니다.
6. 한도(RPM/TPM)는 걸지 않았다. 한도를 건 상태와 Redis 경유 성능은 별도 시험이다.
7. 1초 조건의 "밀린 요청" 200~250건은 k6 가 동시 접속 수백 개를 처음 띄우는 동안의 손실로 보이며 세 대상에 비슷하게 나왔다. 한계를 넘긴 구간(litellm 1워커의 초당 300건 이상)은 k6 의 동시 접속 상한(500)에 닿아 "밀린 요청" 수가 서버 한계와 생성기 상한이 섞인 값이다. 그 구간은 숫자의 크기보다 "포화됐다"는 사실만 본다.
8. `docker stats` 샘플이 2초 안팎 간격이라 CPU·메모리 최대는 근사치다.
9. litellm 은 수정 전후와 무관해 다시 재지 않았고, 우리 쪽만 고친 뒤 다시 쟀다. 두 측정은 같은 컴퓨터·같은 조건이지만 시각이 다르다.

## 시험 도구에서 겪은 함정

다음에 같은 실수를 하지 않으려고 남긴다.

1. **가짜 업스트림이 모든 응답에 같은 `id` 를 주면 litellm 이 사용량 기록을 한 행으로 합친다.** litellm 은 응답 `id` 를 사용량 기록의 기본 키로 써서, 1400건 넘게 처리하고도 기록이 1건이었다(비용 집계는 정확했다). 이대로 비교했다면 litellm 이 DB 쓰기를 거의 안 하는 상태로 재서 **우리에게 불리하게 왜곡**됐을 것이다(5초짜리 스모크 시험에서 고치기 전후로 litellm 1워커의 초당 100건 p50 이 55.5ms 에서 81.8ms 로 늘었다. 이 수치는 본시험 값이 아니다). **정합성 확인(요청 수 대 DB 기록 수)이 이것을 잡았다. 이 단계를 빼지 않는다.**
2. 두 쪽 모델에 같은 단가를 줬다(비용 집계 경로를 같이 타게 하려는 조치). 단가가 없을 때 litellm 이 기록을 건너뛰는지는 확인하지 않았다(1번이 원인이었다).
3. litellm 의 워커 수에 따라 결과가 크게 다르다. 1워커만 비교하면 불공정하다.
4. k6 의 동시 접속 상한(`MAX_VUS`, 기본 500)에 닿으면 "VU 부족" 경고가 나온다. 업스트림이 느릴수록 더 많은 동시 접속이 필요하다.
5. **앞 시나리오가 남긴 닫힌 연결이 다음 시나리오에 영향을 줄 수 있다.** 이번에는 우리 결함 때문에 동시 접속 200 직후의 초당 300건 시험이 실패했다. 시나리오 순서를 바꿔 다시 재 보면 이런 이월 효과를 찾을 수 있다.
6. 실패의 **종류**를 모르면 원인을 못 찾는다. `k6/chat.js` 가 응답 코드별 개수와 실패 응답 샘플을 남기고, `run.sh` 가 서버 로그(`<대상>-container.log`)를 저장한다. 이 첫 측정에는 이 기능이 없어서 한 번 더 재야 했다.

## 다시 재는 방법

```sh
cd bench
RUN_ID=2026-12-01-fast ./run.sh gateway      # 업스트림 50ms(기본)
RUN_ID=2026-12-01-fast ./run.sh litellm1     # 1워커(dell 과 같은 방식)
RUN_ID=2026-12-01-fast ./run.sh litellm4     # 4워커
./compare.py 2026-12-01-fast                 # 세 대상을 시나리오별 표로

# 실제 모델에 가까운 조건(업스트림 1초)
UPSTREAM_DELAY=1s UPSTREAM_TTFT=300ms UPSTREAM_CHUNK_DELAY=40ms \
  SCENARIOS="rate-100 rate-300 vus-10 vus-50 vus-200 stream-rate-100" RUN_ID=2026-12-01-real1s ./run.sh gateway
```

- 세 대상은 **같은 `RUN_ID`** 로 돌려야 `compare.py` 가 한 표로 묶는다
- 준비물: Docker Desktop, `go`(`/opt/homebrew/bin`), 로컬 이미지 `litellm:airgap`. k6 이미지(`grafana/k6:1.0.0`)와 `postgres:16-alpine` 은 처음 실행할 때 받는다
- 한 대상에 4~5분, 세 대상에 약 14분. 돌리는 동안 **이 컴퓨터에서 다른 무거운 작업을 하지 않는다**(같은 자원을 쓰므로 결과가 흔들린다)
- `QUICK=1` 은 스크립트 검증용(짧게)이다. 결과를 비교에 쓰지 않는다
- 원본 결과(JSON, k6 로그, 자원 샘플, 서버 로그)는 `bench/results/<RUN_ID>/` 에 쌓이고 **git 에서 제외**된다. 이 문서의 부록에 전체 표를 남겼다
