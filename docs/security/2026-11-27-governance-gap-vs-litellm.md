# litellm 대비 보안·거버넌스 공백 (2026-11-27)

> 기준: llm-gateway 커밋 `b393d3f`. 비교 대상은 이 저장소 옆의 litellm 포크(`../gateway`, 조사 문서 `docs/litellm-inventory/`)다.
> 이 문서는 **우리에게 없는 것**을 정리한 목록이다. "없음"은 코드·스키마·대시보드 응답을 확인해 찾지 못했다는 뜻이고, 확인이 덜 된 항목은 "확인하지 못한 것"에 따로 적었다.
> 고객사 보안 점검표(15대 보안통제) 양식의 판정이 아니다. 그 판정은 `security-audit` 스킬로 따로 한다.

## 요약

- **가장 큰 공백은 가드레일**이다. 콘텐츠 필터·PII 마스킹 등 요청·응답 통제가 전혀 없다. 조사 문서는 로컬 콘텐츠 필터를 "폐쇄망 내 유일한 완전 로컬 필터, 필수"로 분류했는데 구현하지 않았다.
- **전송 구간**은 2026-11-28 에 게이트웨이 직접 종단(`GATEWAY_TLS_CERT_FILE`·`KEY_FILE`)과 앞단 종단 문서(`docs/security/tls.md`)를 갖췄다. 설정하지 않으면 여전히 평문이다(기동 로그 경고).
- **감사 로그**는 2026-11-28 에 관리 변경 전반(모델·설정·초대·조직·프로젝트·태그·고객·프로바이더·팀 권한)과 로그인·로그아웃·비밀번호 변경까지 넓혔다. 남은 공백은 5장 표에 있다(이전 값, 거절된 요청, 보존 기간).
- **인증 자동화가 없다.** Keycloak 토큰으로 API 직접 호출, SSO 그룹 → 팀·역할 매핑이 없다.
- **키 정책이 약하다.** IP 제한, 자동 회전이 없다.
- **한도의 세분화가 없다.** 일 단위 토큰, 모델별·태그·고객별 예산이 없다.
- 반대로 라우트 권한 허용 목록, 기본 켜진 감사 로그, 로그인 시도 제한 등은 우리가 낫다(아래).

## 3. 예산·한도

한도 대상은 키·팀·사용자·팀원 4종뿐이다(`limit_policy.scope`).

| 기능 | 상태 | 근거 |
|---|---|---|
| 일 단위 토큰 한도(TPD) | **구현함(2026-11-27)** | 키·팀·사용자 `tpd_limit`. UTC 자정에 리셋, 넘으면 429. litellm 처럼 이미 쓴 양만 보므로 마지막 요청은 한도를 넘어 통과할 수 있다 |
| 모델별 예산·모델별 RPM/TPM | **구현함(2026-11-27)** | 키·팀·사용자의 `model_max_budget`(`{모델: {max_budget, budget_duration, rpm_limit, tpm_limit}}`). 요청한 모델 이름과 정확히 같을 때만 걸리고(패턴·액세스 그룹 이름 없음), 응답 뒤 모델별 사용액이 쌓이며 주기마다 리셋. litellm 의 별도 필드 `model_rpm_limit`·`model_tpm_limit` 는 지원하지 않는다(대시보드가 보내지 않는 API 전용 필드). litellm 에서는 유료 기능인데 우리는 막지 않는다 |
| 임시 예산 증액(기한부) | 없음 | |
| 고객(end-user) 단위 예산·한도 | **구현함(2026-11-28)** | 요청의 `user`(또는 `x-litellm-customer-id` 헤더, `metadata.user_id`)로 식별. `/customer/new·update·delete·block·unblock·info·list`(관리자 전용)로 관리하고 예산·RPM·TPM·TPD·모델별 한도는 키·팀과 같은 필드다. `user` 는 호출자가 정하는 값이라 속일 수 있다(litellm 도 같다). 차단·한도는 `user` 를 보낸 요청에만 걸린다 |
| 태그 단위 예산·한도 | **구현함(2026-11-28)** | 요청이 붙인 태그(헤더 `x-litellm-tags`, 본문 `tags`·`metadata.tags`·`litellm_metadata.tags`, 요청당 20개까지) 중 등록한 태그에 예산·RPM·TPM·TPD·모델별 한도가 걸린다. 태그는 호출자가 정하는 값이라 속일 수 있다. 등록하지 않은 태그와 고객은 한도 행을 만들지 않는다. litellm 에서는 유료 기능인데 우리는 막지 않는다. 태그 목록 응답은 litellm 원본(배열) 대신 대시보드 타입(이름→태그 사전)을 따른다 |
| 프로바이더 단위 예산 | **구현함(2026-11-28)** | 프로바이더(모델 배포의 provider 이름)별 예산·주기. 다 쓰면 그 프로바이더의 배포를 후보에서 빼고, 같은 모델의 다른 배포가 없으면 429. litellm 은 설정 파일에 적고 조회(`GET /provider/budgets`)만 있는데 우리는 설정 파일이 없어 쓰기 API(`POST /provider/budgets`, `DELETE /provider/budgets/{provider}`, 관리자 전용)를 더했다. 리셋은 예산 리셋 작업(1분 주기)이 하므로 리셋 시각이 지나도 최대 1분 막혀 있을 수 있다. 429 문구는 litellm 원문을 확인하지 못했다. 배포 단위 예산(`max_budget`)은 없다 |
| 프로젝트(팀 아래 키 묶음)와 그 예산·한도 | **구현함(2026-11-28)** | `/project/new·update·info·list·delete`(대시보드 Projects 화면). 팀 필수, 키의 프로젝트는 선택(`project_id`, 프로젝트의 팀과 키의 팀이 같아야 함). 프로젝트의 차단·허용 모델·예산·RPM·TPM·TPD·모델별 한도가 그 프로젝트 키의 요청마다 걸린다. 조회는 로그인한 누구나(자기 팀 프로젝트만), 만들기·고치기·지우기는 관리자만이다(litellm 화면은 팀 관리자에게도 버튼을 보이지만 우리는 막는다). 키가 남은 프로젝트는 지우거나 팀을 옮길 수 없다. litellm 에서는 enterprise 기능인데 우리는 막지 않는다 |
| 조직 단위 예산·한도·구성원 | **구현함(2026-11-28)** | `/organization/new`, `/v2/organization/{id}`, `/delete`, `/list`, `/info`, `/member_add·update·delete`(대시보드 Organizations 화면). 팀은 조직에 속할 수 있고(`organization_id`), litellm 처럼 팀을 만들거나 고칠 때 팀의 모델·예산·RPM·TPM 이 조직 상한 안인지 검사한다(요청 때는 조직 예산·한도만 본다. 조직 값을 나중에 줄여도 기존 팀은 그대로). 만들기·고치기·지우기·구성원 관리는 관리자만이고 **조직 관리자(`org_admin`) 역할은 없다**: 구성원의 역할 문자열은 화면에 보이는 정보일 뿐 권한이 아니다. 조회는 로그인한 누구나 부르지만 관리자가 아니면 빈 목록이다. 팀이 남은 조직은 지울 수 없다. 키에는 조직을 따로 두지 않고 키의 팀이 속한 조직이 적용된다(키 생성의 `organization_id` 는 읽지 않고, 팀 없는 키는 조직 한도를 받지 않는다). litellm 에서는 라이선스 기능인데 우리는 막지 않는다 |
| 소프트 예산 알림 | **일부 구현(2026-11-27)** | Slack·이메일 알림은 없다(폐쇄망). 대신 `/metrics` 의 `gateway_soft_budget_exceeded{scope}` 가 소프트 예산 이상인 대상 수를 알려 사내 Prometheus 알람이 쓴다. 화면 경고는 없다 |
| Redis 장애 시 요청 거부(fail-closed) 선택 | **구현함(2026-11-27)** | `GATEWAY_LIMITS_FAIL_CLOSED=true`(redis 저장소 전용). 기본은 메모리 카운터로 이어서 처리 |

## 5. 감사·기록

| 기능 | 상태 | 근거 |
|---|---|---|
| 감사 로그 범위 | **넓힘(2026-11-28)** | 관리 API 의 성공한 쓰기는 모두 기록한다(키·팀·사용자에 더해 모델 배포, 설정, 초대, 조직·구성원, 프로젝트, 태그, 고객, 프로바이더 예산, 팀 권한·팀원 한도, IP 허용 목록). 로그인 성공·실패(대시보드·CLI·SSO), 로그아웃, 비밀번호 변경, 초대 수락도 기록한다(행위자·접속 주소·방법, 비밀번호는 없음). 요청 본문의 비밀 값(`api_key`·`password`·`*secret*` 등)은 중첩된 곳에서도 뺀다 |
| 감사 로그의 남은 공백 | **있음** | ① (해소, 2026-11-28) 이전 값(`before_value`)을 남긴다: 키·팀·사용자·모델·조직·프로젝트·태그·고객과 화면 설정·IP 허용 목록·프로바이더 예산을 바꾸거나 지울 때 처리 전의 모습(응답 행과 같은 모양, 비밀 제외)이 함께 기록된다. 만들기는 이전 값이 없다. 구성원·초대·모델 허브 설정은 읽을 수 있는 한 줄이 없어 이전 값 없이 기록하고, 한 요청의 대상이 50개를 넘으면(일괄 삭제 등) 이전 값을 읽지 않는다. ② 거절된 요청(권한 없음, 검증 실패)과 조회는 기록하지 않는다. ③ 로그인 시도 제한에 걸린 요청은 기록하지 않는다(공격자가 기록을 불리지 못하게). 제한이 걸리기 전 실패 시도는 남는다. ④ (해소, 2026-11-28) 보존 기간은 `GATEWAY_AUDIT_RETENTION_DAYS`(기본 365일, 0 은 영구)로 정한다. 지난 기록은 하루마다 나눠 지우고 지운 사실을 `retention_purged` 한 줄로 남긴다. 다만 삭제 전에 외부로 내보내는 길은 없어서, 오래 보관해야 하는 고객사는 DB 백업이나 이 값을 늘려 대응해야 한다. ⑤ 변조 방지(해시 연결, 외부 전송)가 없다. DB 관리자는 감사 기록도 고칠 수 있다. ⑥ 추론 요청의 본문은 여전히 남기지 않는다 |
| 요청·응답 본문 저장(감사·조사용, 기본 꺼짐) | **없음** | 설계 13장은 "기본 끄고 설정으로 켤 수 있게"였으나 미구현. 지금은 본문을 전혀 남기지 않는다(프라이버시에는 유리, 사고 조사에는 불리) |
| 외부 로깅 연동(Langfuse 등) | 없음 | 폐쇄망이라 외부 SaaS 는 제외했지만 사내 Langfuse 연동은 선택지였음. 대시보드 콜백 설정은 빈 응답 |
| Slack·이메일 알림 | 없음 | `F_extras.md` 34·67행: 후순위(Slack/SMTP 외부 연동) |

## 6. 데이터 보호·전송

| 기능 | 상태 | 근거 |
|---|---|---|
| 게이트웨이 자체 TLS | **구현함(2026-11-28)** | `GATEWAY_TLS_CERT_FILE`·`GATEWAY_TLS_KEY_FILE`(함께 정해야 기동). TLS 1.2 이상, HSTS, 인증서 파일을 바꾸면 재기동 없이 다시 읽음. 앞단 종단 배치는 `X-Forwarded-Proto` 를 신뢰하는 앞단(`GATEWAY_TRUSTED_PROXIES`)에서만 믿어 대시보드 쿠키에 `Secure` 를 붙인다. 구성 방법은 `docs/security/tls.md`. 설정하지 않으면 평문이고 기동 로그에 경고. 업스트림(Ollama) 구간과 mTLS 는 범위 밖 |
| 외부 시크릿 매니저 연동(Vault·AWS 등) | 없음 | 마스터 키·DB 비밀번호는 환경 변수뿐 |
| 마스터 키 교체 | 불편 | 마스터 키에서 업스트림 키 암호화 키·로그인 키·세션 서명 키를 파생하므로, 바꾸면 업스트림 키(모델 편집에서 다시 입력)·로그인 키·세션·초대 링크가 무효가 됨 |

## 우리가 낫거나 같은 점

- 라우트 권한을 **허용 목록**으로 선언해야만 등록된다(`core.Route` 에 권한 선언 필수). litellm 은 차단 목록이라 새 API 를 빠뜨리면 뚫린다. 시험으로 팀 admin 이 관리자 계정을 가로채는 길도 막았다(커밋 `3d13fbe`).
- **감사 로그가 기본으로 켜져 있다.** 이 포크의 litellm 은 `store_audit_logs` 설정이나 `LITELLM_STORE_AUDIT_LOGS` 환경 변수로 명시해야 켜지고, 아무것도 정하지 않으면 유료 사용자일 때만 켜진다(`litellm/proxy/management_helpers/audit_logs.py`).
- 로그인 시도 제한(아이디·IP 조합과 IP 총량), 계정 존재 노출 방지, 비밀번호 PBKDF2-SHA256 600,000회, 키는 해시로만 저장, 업스트림 키는 AES-256-GCM 으로 봉해 저장.
- 외부 호출 0(텔레메트리·업데이트 확인·가격표 내려받기 없음), 사용량 기록 90일 자동 삭제.
- 요청·응답 본문을 기본으로 남기지 않는다.

## 확인하지 못한 것

1. (해소) 감사 대상이 아니던 쓰기 라우트를 2026-11-28 에 하나씩 확인해 모두 감쌌다. 다만 `/tag/info` 처럼 POST 이지만 읽기인 라우트는 감사 대상이 아니다.
2. JWT 직접 인증과 SSO 그룹 매핑은 코드 검색(`grep`)으로 찾지 못한 것이다. 다른 이름으로 구현돼 있을 가능성은 낮지만 완전히 배제하지는 못했다.
3. litellm 쪽 기능의 존재는 `docs/litellm-inventory/` 조사 문서와 이 포크의 소스를 근거로 했다. 로컬에서 실제로 돌려 확인한 것은 이번에 하지 않았다.
4. 위 공백이 고객사의 실제 요구에 해당하는지는 모른다. 특히 가드레일은 고객사별로 필수 여부가 다르다.
5. 이 목록은 기능의 **유무**만 다룬다. 있는 기능의 구현 품질(예: 우리 인증 코드의 취약점)은 `security-audit` 스킬이나 별도 점검이 필요하다. 이 세션에서 점검한 것은 비밀번호 처리, 초대 링크, 로그인 시도 제한이고, 재설정 링크·대시보드 쿠키 속성·로그인 외 엔드포인트의 계정 존재 노출은 점검하지 못했다.
